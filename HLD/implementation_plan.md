# Planet Survival 实现计划

## 1. 目标与原则

本计划用于将当前 Unity 原型骨架逐步扩展为可玩的 2.5D 第三人称生存游戏。开发采用纵向切片：每个阶段都应形成可以启动、操作和验收的版本，避免同时铺开大量未完成系统。

开发过程中遵循以下原则：

- 优先完成核心生存循环，再增加内容量和视觉表现。
- 先用简单实现验证玩法，再根据 Profiler 和实际需求优化。
- 配置数据与运行时状态分离，核心规则尽量使用普通 C# 类。
- 每个阶段完成后消除编译错误，并执行相关 Edit Mode、Play Mode 和手工测试。
- 新阶段开始前先修复上一阶段影响主流程的缺陷。

## 2. 整体里程碑

| 阶段 | 目标 | 完成后的可玩结果 |
| --- | --- | --- |
| 0 | 项目骨架 | 自动生成地形、玩家、相机和基础生存状态 |
| 1 | 正式启动与场景 | 可以从 Bootstrap 场景可靠进入游戏 |
| 2 | 生存状态 UI | 可以观察四项属性和游戏时间变化 |
| 3 | 物品、背包与消耗品 | 可以拾取、携带、管理并消耗物品恢复状态 |
| 4 | 昼夜与环境 | 时间、光照和自然衰减形成生存压力 |
| 5 | 采集与资源 | 可以从世界获取基础资源 |
| 6 | 建造与设备 | 可以消耗资源放置生存设备 |
| 7 | 状态效果 | 疾病、受伤和环境影响能改变角色状态 |
| 8 | 地下勘测 | 可以勘测并开采格子下方资源 |
| 9 | 存档与读档 | 可以可靠恢复世界、角色和进度 |
| 10 | 获救与完整循环 | 能坚持目标天数并完成或失败一局游戏 |
| 11 | 优化与内容生产 | 支持更大地图、更多内容和稳定构建 |

## 3. 分阶段实施

### 当前实施进度

- 阶段 0：工程已迁移至 Unity 6000.2.9f1，脚本编译成功；核心规则和基础运行流程测试通过。
- 阶段 1：已完成正式场景、持久化 `GameFlow`、Bootstrap 组合根、配置资产、主菜单及暂停/继续/重开/返回菜单流程。
- 阶段 2：已实现事件驱动的四项生存状态 HUD、危险阈值反馈、日期/时间/救援倒计时、交互提示与设置面板占位。
- 生存规则扩展：精神、饱食或口渴归零后会按归零项数叠加扣除生命；生命归零会进入 `GameOver`，暂停游戏并显示重开/返回菜单界面。
- 自动验证：14 项 Edit Mode 测试和 1 项完整场景 Play Mode 测试全部通过。
- 阶段 3：已提前合并原阶段 5 的物品与背包范围；领域模型、快捷栏引用、世界拾取和消耗品效果已开始实现。
- 下一步：完成阶段 3 的背包 UI、拖拽、丢弃世界物和场景内示例配置，并补齐 Play Mode 验收。

### 阶段 0：确认现有骨架

当前状态：已完成自动化验收；玩家操作和视觉效果仍建议在编辑器中人工确认。

工作内容：

- 使用项目锁定的 Unity 6000.2.9f1 打开工程，等待资源导入完成。
- 修复首次导入时出现的编译错误或 API 兼容问题。
- 在空场景中进入 Play Mode，验证运行时启动器。
- 执行现有 Edit Mode 测试。
- 记录实际 Unity 补丁版本，并更新 `ProjectVersion.txt`。

验收标准：

- Console 没有编译错误。
- 玩家可以使用 WASD 移动，相机正常跟随。
- 地图有随机起伏和地下厚度。
- `VitalTests` 与 `GridMapTests` 全部通过。

### 阶段 1：正式启动流程与场景

目标：将自动生成原型改造成可维护的正式场景入口。

工作内容：

- 创建 `Bootstrap`、`MainMenu` 和 `Gameplay` 场景。
- 创建负责切换游戏状态的 `GameFlow`，状态至少包括启动、主菜单、加载、游戏中、暂停和结束。
- 将全局服务的创建集中到 Bootstrap 组合根。
- 使用场景中的配置资产替代硬编码的默认地图设置。
- 添加暂停、退出当前游戏和重新开始功能。
- 明确跨场景对象的所有权和销毁时机。

建议模块：

- `Core/Flow`
- `Core/SceneManagement`
- `Core/Configuration`

验收标准：

- 游戏始终从 Bootstrap 进入，不依赖当前打开的编辑器场景。
- 可以从主菜单开始游戏、暂停、继续并返回主菜单。
- 重复进入 Gameplay 不会产生重复相机、时钟或玩家。

### 阶段 2：生存状态与 HUD

目标：让玩家能够清楚理解当前生存状况。

工作内容：

- 创建健康、精神、饱食和口渴的 HUD。
- 显示当前天数、当天时间和距离获救的剩余天数。
- UI 通过属性变化事件刷新，不在每帧轮询全部数据。
- 为危险阈值增加颜色或图标反馈。
- 创建简单的交互提示，例如“按 E 饮用”。
- 添加暂停菜单和基础设置面板占位。

建议模块：

- `UI/HUD`
- `UI/Interaction`
- `UI/Menu`

验收标准：

- 四项属性变化后 UI 立即且正确刷新。
- UI 显示值与领域模型一致。
- 不同分辨率和常见宽高比下 UI 不重叠。
- 玩家靠近交互物时能看到正确提示。

### 阶段 3：物品、背包与消耗品闭环

目标：形成“寻找资源—放入背包—管理或快捷使用—恢复状态”的完整纵向切片。

工作内容：

- 使用 ScriptableObject 定义 `ItemDefinition`。
- 实现纯 C# 的 `Inventory`、`ItemStack` 与 `QuickBarConfiguration`。
- 支持容量、堆叠上限、原子添加、移除、使用和丢弃。
- 实现食物和饮水效果，允许一个物品影响多项属性。
- 创建世界拾取物、拾取交互、背包使用和快捷使用流程。
- 为物品增加唯一且稳定的字符串 ID。
- 添加少量示例配置：应急口粮、水袋和医疗包。
- 实现背包 UI、物品详情、快捷栏和拖拽配置。
- 区分物品定义与运行时堆叠；快捷栏只保存稳定堆叠 ID，不拥有物品。
- 明确饱食度临时溢出及健康状态限制的规则。

建议模块：

- `Items/Definitions`
- `Items/Effects`
- `Items/World`
- `Inventory/Domain`
- `Inventory/Application`
- `UI/Inventory`

验收标准：

- 玩家可以拾取、堆叠、管理并消耗食物和水。
- 满背包、部分移除和丢弃行为正确，失败操作不会丢失或复制物品。
- 快捷栏操作只改变引用和顺序，不改变物品数量与容量。
- 属性不会超出规则允许的范围。
- 配置错误或缺失引用会给出明确诊断信息。
- 背包核心规则和物品效果具有 Edit Mode 测试，无需运行场景即可验证。

### 阶段 4：游戏时间、昼夜与基础环境

目标：通过时间和环境形成连续生存压力。

工作内容：

- 将 `GameClock` 扩展为独立、可暂停、可调整速度的时间模型。
- 添加昼夜光照、天空颜色和环境亮度变化。
- 根据游戏时间驱动饱食和口渴衰减。
- 为睡眠、强烈日照和低氧预留环境影响接口。
- 将大气成分设为单局配置，并根据高度计算氧气比例。
- 统一处理暂停状态，暂停时生存数值不得继续衰减。

建议模块：

- `World/Time`
- `World/Environment`
- `World/Atmosphere`

验收标准：

- 一天能够完整循环，天数切换准确。
- 调整时间倍率不会导致属性计算出现帧率差异。
- 暂停和恢复不会重复计算或遗漏时间。
- 相同输入与时间步得到相同的属性结果。

### 阶段 5：资源节点与采集

目标：建立探索和资源获取循环。

工作内容：

- 定义资源类型、资源节点和采集产出表。
- 实现采集距离、采集时间、工具要求和资源耗尽。
- 为石头、残骸、植物等创建第一批资源节点。
- 支持资源节点的生成规则和最低出生间距。
- 采集过程可取消，取消后状态必须正确复原。
- 将采集结果接入背包容量判断。

建议模块：

- `Gathering/Definitions`
- `Gathering/Runtime`
- `World/Spawning`

验收标准：

- 玩家可以定位、采集并获得资源。
- 背包满时不会销毁未能接收的资源。
- 资源耗尽后的表现和碰撞状态正确。
- 相同世界种子产生可复现的初始资源分布。

### 阶段 6：配方、建造与设备

目标：允许玩家消耗资源改善生存条件。

工作内容：

- 使用 ScriptableObject 定义配方和建筑定义。
- 实现建造预览、旋转、格子占用和放置合法性检查。
- 只有放置成功后才扣除材料，失败时不得丢失资源。
- 实现拆除与可配置的资源返还比例。
- 首批设备建议包括储水器、氧气设备、种植箱和信标。
- 将设备逻辑拆为独立能力组件，例如供能、储存、生产和交互。

建议模块：

- `Crafting`
- `Building/Placement`
- `Building/Runtime`
- `Devices`

验收标准：

- 建筑不能超出地图边界或与占用格重叠。
- 建造、取消和拆除不会复制或无故丢失资源。
- 新增建筑主要通过配置和组合组件完成。

### 阶段 7：状态效果与伤害

目标：统一处理被动影响、疾病和持续状态变化。

工作内容：

- 建立伤害请求、伤害类型和抗性模型。
- 建立可计时、可叠加或可刷新的状态效果系统。
- 实现晒伤、脱水、饥饿、低氧和受伤等首批效果。
- 明确效果叠加规则、移除规则和存档数据。
- 将角色死亡从属性模型中发出，由游戏流程处理结束状态。
- UI 显示当前效果、持续时间和来源。

建议模块：

- `Combat/Damage`
- `StatusEffects`
- `UI/StatusEffects`

验收标准：

- 状态效果重复施加符合各自叠加规则。
- 对象禁用或销毁后不遗留计时器和事件订阅。
- 健康归零只触发一次死亡流程。

### 阶段 8：地下数据、勘测与挖掘

目标：实现不进入地下的资源探测与开采玩法。

工作内容：

- 为每个地图格生成地下层数据和资源储量。
- 将地下数据与地表表现分离，不为每个地下单元创建 GameObject。
- 实现勘测范围、精度和结果可视化。
- 实现挖掘设备安装、工作周期、能耗和产出。
- 记录已探测、已开采和剩余储量。
- 使用确定性随机生成确保同一存档可重建未修改区域。

建议模块：

- `World/Underground`
- `Surveying`
- `Extraction`

验收标准：

- 未勘测格不会泄露精确资源信息。
- 开采产出不超过地下储量。
- 大地图地下数据不会产生同等数量的场景对象。

### 阶段 9：存档与读档

目标：可靠保存一局游戏的完整进度。

工作内容：

- 定义带版本号的存档 DTO，不直接序列化 MonoBehaviour。
- 保存玩家状态、背包、时间、世界种子、资源节点、建筑和地下修改。
- 为场景实体建立稳定运行时 ID。
- 实现手动存档、自动存档、原子写入和备份文件。
- 校验损坏或版本不兼容的存档，并提供明确提示。
- 为后续字段变化建立迁移入口。

建议模块：

- `Persistence/Contracts`
- `Persistence/Serialization`
- `Persistence/Migrations`

验收标准：

- 保存后退出并重新进入，关键状态一致。
- 写入中断不会破坏上一份有效存档。
- 未知或损坏存档不会导致游戏无提示崩溃。
- 至少有一次旧版本到新版本的迁移测试样例。

### 阶段 10：获救目标与完整游戏循环

目标：形成有开始、过程、成功和失败的完整一局。

工作内容：

- 配置目标生存天数和获救条件。
- 实现迫降开场、目标提示和阶段性事件。
- 实现信标或通讯设备等最终目标条件。
- 实现成功、死亡和放弃三种结束流程。
- 增加结算数据：生存天数、采集资源、建造设备和状态变化。
- 完成一轮难度调参，让资源供给与消耗形成合理压力。

验收标准：

- 新玩家能够理解当前目标和失败原因。
- 一局游戏可以从主菜单完整进行到成功或失败，再返回主菜单。
- 所有结束路径不会遗留场景对象或污染下一局状态。

### 阶段 11：性能、表现与内容生产

目标：从功能原型过渡到可持续制作内容的版本。

工作内容：

- 使用 Profiler 测量 CPU、GPU、GC 和内存，不凭感觉优化。
- 将逐格 GameObject 地形替换为 Chunk Mesh、合批或合适的地形方案。
- 为重复生成对象引入对象池，并定义完整的重置契约。
- 根据实际资源规模决定是否引入 Addressables。
- 增加动画状态机、音效、粒子、后处理和环境表现。
- 建立配置校验工具、开发者控制台和调试可视化。
- 建立目标平台构建流程和性能预算。

验收标准：

- 目标硬件上达到约定帧率和内存预算。
- 长时间游玩没有持续增长的内存或事件订阅泄漏。
- 内容配置错误能够在编辑器阶段被发现。
- 可以生成并运行独立构建版本。

## 4. 推荐的系统依赖方向

依赖应尽量保持单向：

```text
UI / Scene / Unity Components
              ↓
Application Use Cases
              ↓
Domain Models and Interfaces
              ↑
Infrastructure Adapters
```

具体约束：

- UI 可以调用应用层，但核心规则不能引用 UI。
- 背包可以引用物品定义，物品定义不能引用具体背包 UI。
- 建造系统通过背包接口消费材料，不直接操作背包内部集合。
- 存档系统读取公开快照，不通过反射抓取场景组件私有字段。
- 世界表现读取地图数据，地图数据不依赖 MeshRenderer 或 GameObject。

## 5. 测试策略

### Edit Mode 测试

优先覆盖：

- 属性上下限、最大值修正和临时溢出。
- 时间换算与自然衰减。
- 物品效果、堆叠和背包容量。
- 配方材料检查与事务式扣除。
- 建筑占格判断。
- 状态效果叠加。
- 地下资源生成和存档迁移。

### Play Mode 测试

优先覆盖：

- Bootstrap 和场景切换。
- 玩家移动、交互范围和事件解绑。
- UI 与玩家状态绑定。
- 建筑放置和世界对象恢复。
- 暂停、返回菜单和重新开始。

### 手工测试

每个里程碑至少执行一次：

- 从主菜单开始新游戏。
- 完成该阶段新增的主要玩家流程。
- 测试失败、取消、背包满和重复操作。
- 暂停、恢复、返回菜单后再次进入。
- 检查 Console 是否出现异常、错误或高频日志。

## 6. 初期暂不实现

以下内容应等待核心循环验证后再决定：

- 多人联网。
- ECS/DOTS 全面重构。
- 球形星球地图。
- 无缝无限世界。
- 复杂战斗与大量敌人 AI。
- 完整科技树和大规模任务系统。
- 自研通用依赖注入或事件总线框架。

这些功能会显著扩大工程复杂度，但不会帮助早期验证“采集资源、维持生存、建设设备并等待获救”的核心体验。

## 7. 下一步任务清单

开始阶段 1 时，建议按以下顺序执行：

1. 用 Unity Editor 打开当前项目并消除全部编译错误。
2. 创建并保存 Bootstrap、MainMenu、Gameplay 三个场景。
3. 将三个场景加入 Build Settings。
4. 创建 `GameFlow` 状态模型和场景切换服务。
5. 将当前 `GameBootstrap` 的默认配置迁移到 ScriptableObject 资产。
6. 添加主菜单、暂停和返回主菜单流程。
7. 编写场景重复进入的 Play Mode 回归测试。
8. 完成阶段 1 验收后，再进入 HUD 开发。
